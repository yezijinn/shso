# 文档规范

仓库内所有 Markdown 文档（含工作区归档）统一遵循本规范。

## 写作准则

1. **结论先行**：章节首句给结论，再给依据。禁止铺垫、悬念、设问。
2. **陈述句为主**：使用「应为 / 实测为 / 约束为」，不使用「我们」「大家」「其实」「不得不说」等对话词。
3. **零修饰**：禁用 emoji、感叹号、加粗堆砌、火焰/警告图标装饰、营销与宣传口吻。
4. **不写过程叙事**：不记录「先尝试 A，发现不行，又改成 B」。只保留结论、原因、证据。过程属 git 历史。
5. **数据须有出处**：数值标注来源（真机型号 / 单测任务 / commit）。无出处的估计值不写。
6. **术语一致**：同一概念全文同一写法；技术术语保留英文原文（`Compose`、`SELinux`、`Zip Slip`）。
7. **中英混排空格**：中文与英文/数字之间加空格。

## 格式

| 项 | 规则 |
|---|---|
| 标题层级 | 最多三级；一级标题每文件仅一个 |
| 列表 | 一行一条，结尾不加句号以外的标点堆砌；同级结构平行 |
| 表格 | 多维对比、参数清单、映射关系一律用表格 |
| 代码与路径 | 反引号包裹，带语言标注的代码块 |
| 日期 | `YYYY-MM-DD` |
| 状态标记 | `[ ]` 待办 / `[/]` 进行中 / `[x]` 完成 / `[!]` 阻塞 |
| 引用 | 引用路径用相对链接，跨目录写明源位置 |

## 文档职责边界

| 文档 | 写 | 不写 |
|---|---|---|
| `README.md` | 功能、环境、构建、安全模型、版本规则 | 更新日志、实现细节 |
| `更新日志.md` | 变更清单，一行一条，日期倒序 | 实现细节、过程 |
| `docs/PROJECT.md` | 技术栈、架构、安全子系统、构建约束、已知注意点 | 重复 README 的功能清单 |
| `module/shso_guard/README.md` | 守卫原理、策略、覆盖范围、能力边界 | App 侧审查细节 |
| `docs/在线编译.md` | Actions 自定义包名编译步骤与 FAQ | 本地构建 |
| `TASKS.md` | 当前看板、已定结论、真机备忘 | 已归档的历史过程 |

## 维护流程

改动功能后：代码 → 单测 → `更新日志.md` → `README.md` / `PROJECT.md`（仅当影响用法或约束）→ 提交。

归档文档须在首部标明适用范围与「以现行文档为准」的指向，避免与 `README.md` / `docs/PROJECT.md` 冲突。
